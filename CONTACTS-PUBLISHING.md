# Parish Contacts publishing (Dev)

Authoritative source: `_content/contacts.json`. The existing six `sections` retain their IDs, titles and eyebrow text: Parish leadership; Parish office & PCC; Worship & life events; Pastoral care & safeguarding; Parish life & communications; PCC members.

The initial 31 published entries comprise 18 contact records and 13 PCC records. A contact has `id`, `section`, `role`, `name`, `status`, optional `phone`, `email` and `groupId`. PCC records have `id`, `name`, `status`. Both record types optionally have `photo`. Display order is array position. Adjacent matching group IDs preserve grouped contact cards. Genuine source data was not edited for this capability.

Authenticated administrators use GET and PUT `/api/contacts`. Both apply the existing verified Easy Auth administrator policy. The deployment's Easy Auth perimeter rejects unauthenticated or spoofed-header requests. The API uses server-side GitHub App credentials and hard-codes `micklehamchurch/website`, branch `Dev`, metadata path `_content/contacts.json` and the approved generated image path `assets/images/contacts/profiles/`. Request selectors and extra fields are rejected; no arbitrary writes exist.

Opening Contacts loads the shared source, including drafts, and its blob SHA plus the actual Dev HEAD SHA. Old browser-session Contacts data is ignored. Add/edit, category changes, draft/restore, PCC order and confirmed permanent deletion remain staged in memory until Publish changes is confirmed. Refresh loses staged changes. Reload requires confirmation before discarding them. A clean editor disables Publish. Publishing blocks duplicate requests and updates the SHA on success. A stale SHA or GitHub race returns 409; staged data stays available for review/backup and a confirmed reload is required.

Server validation requires the existing root structure and six sections, immutable section metadata during publishing, unique safe IDs across both collections, published/draft status, plain text and bounded field lengths, valid optional email/phone, allowed categories, supported grouping, no unknown ordering fields, and a maximum 256 KiB directory. The JSON request is bounded incrementally, regardless of Content-Length.

Drafts stay in the authenticated shared editor but are excluded from the generated public directory, public Admin projection and search index. Delete stages permanent source removal and explicitly asks for confirmation. Move to draft is the normal temporary hiding action. The public directory retains its existing design. Search reads generated published directory text.

Successful publication says **Contacts published to Dev. The website is rebuilding.** It does not claim Contacts live. Existing content/Pages workflow generates and deploys the public directory/search. Download Contacts backup and the GitHub source link remain under Advanced backup and source; neither is required for ordinary publishing.

## Optional profile photographs

Add/Edit contact and PCC member includes Profile photograph: current preview, Upload / Replace, Remove, and Top/Centre/Bottom framing. The permission reminder asks the church to have permission to publish the photograph. Selection, removal and focal position remain staged until Publish changes. Upload bytes stay in tab memory; no originals are persisted in session storage or the public repository. Existing associated legacy photographs remain valid and unchanged. No new actual photographs are included in the capability implementation.

New photo metadata is optional: `photo: { position: "top" | "center" | "bottom", variants: [{ src, width, height, bytes }] }`. Existing safe legacy string references remain supported. No-photo records require no changes. New variants are server-created UUID-named WebP files under `assets/images/contacts/profiles/`; clients cannot introduce or change asset references. They may retain the same person's current variants, change position, remove a photograph, or supply an upload for that person's ID.

The enhanced PUT body is `{ sha, headSha, contacts, uploads }`; upload entries are `{ contactId, fileName, mimeType, base64, position }`. GET and enhanced successful PUT return `headSha`; PUT also returns the resolved `contacts`, `sha` and `commitSha`. Legacy metadata-only PUT remains supported, but cannot introduce, remove or change photo metadata. Errors preserve existing Contacts categories; uploads additionally use the gallery's safe `album-unsupported-format`, `album-invalid-image` and `album-too-large` categories. HEIC/HEIF messaging asks for JPEG export.

Processing reuses the proven gallery signature/container, extension/MIME, strict base64, corruption/polyglot, animated-image and pixel-limit checks. JPEG/JPG, PNG and static WebP only; 10 MiB per image, six per publish, 20 MiB decoded total, 40 million decoded pixels per image. Request streams are bounded to the gallery's base64 body allowance; contacts metadata remains at most 256 KiB. Filenames from the user never become storage paths. Sharp rotates EXIF orientation, strips EXIF/GPS/XMP/ICC metadata and produces 400/800px maximum-long-edge derivatives (quality 80/84, effort 4), preserving aspect ratio without enlargement or duplicate-size outputs. The church should retain originals separately.

Enhanced publishing reads metadata at an immutable Dev HEAD, checks both blob and HEAD SHAs, fully processes images first, then creates a single Git tree/commit containing optimized assets and metadata. Replaced/removed server-created profile assets are deleted in that same tree when unreferenced. Legacy associated images are retained. Only a non-forced `heads/Dev` update makes the result live; processing/blob/tree/commit failures cannot attach incomplete metadata. Competing updates return 409. Credentials remain in the Azure Function's existing GitHub App chain.

The canonical public page is `our-team.html` (`parish-contact-directory.html` redirects there). Portraits appear beside the person's own canonical contact details and optionally in the PCC member list, not in other phone/email listings. The frame is 88×132px, with responsive `srcset`, `sizes="88px"`, lazy loading, async decoding and alt text equal to the public name. New derivatives use CSS cover with the chosen focal position; full derivatives preserve the original image proportions. Existing legacy image presentation remains intact. Draft records are omitted. Admin previews use the immutable commit's raw image URL, as Photo Albums does, to avoid waiting for Pages deployment.
